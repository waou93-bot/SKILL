# Référencement après déploiement

Contrôler ce socle sur les pages prioritaires réellement publiées. Distinguer réception du sitemap, exploration, indexation et résultats ; adapter les délais de suivi sans multiplier les soumissions ni promettre un effet.

Exécuter les démarches utiles pour le site de production courant, avec les accès disponibles et dans le périmètre demandé par l'utilisateur. Une demande opérationnelle peut autoriser les soumissions officielles gratuites et les configurations de propriété strictement nécessaires sur ce site ; le skill ne crée pas d'autorisation supplémentaire. Un audit ou une validation du skill reste en lecture seule sur les services externes. Ne pas promettre l'indexation, le classement ou une citation IA.

## Identifier le site et reprendre l'existant

Lire les instructions du projet, son domaine de production, ses décisions SEO et IA, les déploiements et le registre des démarches. Réutiliser les skills seo et ai-seo lorsqu'ils sont disponibles, sans déclencher une nouvelle stratégie complète. Ne jamais réutiliser implicitement le domaine, les comptes ou les résultats d'un autre site. Si plusieurs domaines restent plausibles, demander lequel traiter.

Identifier domaine canonique, langues, pays, pages prioritaires, CMS/hébergement, DNS, comptes Google Search Console et Bing Webmaster Tools, accès API et navigateur. Distinguer connecté, autorisé, vérifié et inaccessible. Ne pas demander des mots de passe ni inscrire de secrets dans les rapports. Un compte connecté ne prouve pas la propriété du domaine ciblé.

Lire [les opérateurs et sources](references/operators.md) pour sélectionner les démarches. Vérifier leurs procédures dans la documentation officielle actuelle avant de les appliquer. Couvrir les services pertinents pour le public et l'activité ; « tous les opérateurs » signifie inventorier les possibilités et justifier les exclusions, pas soumettre partout sans discernement.

## Parcours d’indexation Google et Bing

Pour une demande opérationnelle d’indexation, suivre ces étapes sans attendre une validation intermédiaire du rapport. Une proposition ou un audit seul reste en lecture seule. La demande explicite d’indexer le site autorise l’ajout des propriétés GSC et Bing manquantes, la soumission du sitemap valide, jusqu’à 100 soumissions d’URL Bing par exécution et les demandes Google possibles dans le quota réellement affiché par Search Console. Elle n’autorise pas la création d’un compte, la modification DNS, le déploiement du site ou une action payante.

1. **Trouver ou créer les propriétés.** Lister les propriétés visibles dans le compte connecté et réutiliser celle qui couvre exactement le domaine de production. Une propriété Domaine couvre ses sous-domaines et protocoles ; une propriété préfixe couvre seulement son protocole, hôte et chemin. Si la propriété GSC manque dans ce compte, l’ajouter avec l’API Sites.add si elle est disponible, sinon dans l’interface. L’ajout API ne vérifie pas la propriété. Une propriété Domaine requiert une preuve DNS ; ne modifier les DNS que si cette action est explicitement autorisée et accessible. Vérifier ensuite le statut de propriété. Pour Bing, réutiliser le site existant ; sinon importer la propriété vérifiée depuis GSC lorsque les permissions le permettent, puis vérifier qu’elle a bien été ajoutée. À défaut, l’ajouter et la vérifier par une méthode prise en charge. L’absence dans le compte connecté ne prouve pas qu’aucune autre propriété n’existe.
2. **Lire l’état actuel avant les écritures.** Sur une propriété existante, consulter dans GSC le rapport d’indexation des pages, les sitemaps et leur date de traitement. Inspecter les URL prioritaires et celles signalées comme non indexées ; comparer l’âge du rapport global et de l’inspection individuelle. Dans Bing, consulter Search Performance, Sitemaps, Site Explorer et l’inspection d’URL. Distinguer l’état de l’index, le test live et la réception d’une soumission.
3. **Valider l’inventaire d’URL et le sitemap.** Découvrir les sitemaps déclarés dans robots.txt, les index de sitemaps publics et l’inventaire CMS ou routes quand il est accessible. Dédupliquer et normaliser les URL canoniques de production. Vérifier le sitemap et ses enfants, les erreurs HTTP, les redirections, les directives robots/noindex, les canonicals et les dates lastmod. Utiliser un contrôle automatisé sur les URL du sitemap lorsqu’il est faisable ; sinon déclarer la couverture et vérifier au minimum les pages prioritaires et un échantillon par gabarit. Ne pas imposer un audit manuel complet du contenu, du maillage et des intentions avant d’ouvrir GSC ou Bing. Exclure les pages privées, non canoniques, redirigées, bloquées ou volontairement noindex. Si le sitemap contient des URL invalides, ne pas les soumettre ; poursuivre avec les URL valides et consigner la correction nécessaire.
4. **Soumettre le sitemap aux deux moteurs.** S’il est valide et n’est pas déjà correctement déclaré, le soumettre à GSC par l’interface ou l’API Sitemaps.submit, et à Bing Webmaster Tools. Après import GSC dans Bing, vérifier d’abord si le sitemap est déjà présent afin d’éviter les doublons. Si le sitemap a déjà été soumis sans changement, contrôler son dernier statut au lieu de le renvoyer. En l’absence de sitemap ou s’il est défectueux, continuer les diagnostics indépendants ; préparer toute correction dans le périmètre autorisé, sans publier sans autorisation. Un succès de soumission ne prouve ni lecture du sitemap ni indexation des URL.
5. **Demander l’exploration des URL éligibles.** Le sitemap est la voie principale pour faire découvrir un grand ensemble de pages à Google. L’API URL Inspection de GSC est en lecture seule ; la demande d’exploration individuelle passe par l’interface et son quota quotidien peut varier. L’utiliser pour les pages prioritaires nouvelles, mises à jour ou non indexées dont le test live ne révèle pas de blocage. Pour Bing, soumettre jusqu’à 100 URL canoniques éligibles par exécution, ou moins si le quota affiché est inférieur. Si plus de 100 URL sont éligibles, prioriser les pages stratégiques récemment créées ou mises à jour et les URL non indexées sans blocage connu ; noter le reste pour la suite. Ne pas soumettre de nouveau les URL déjà indexées ou inchangées. Bing peut accepter un quota supérieur à 100 : ce plafond de 100 est une limite d’exécution choisie pour le workflow, pas une affirmation sur le quota officiel.
6. **Utiliser IndexNow pour les changements.** Réutiliser l’intégration CMS/CDN existante. Notifier les URL canoniques réellement nouvelles, modifiées ou supprimées, selon la clé, la portée et les formats documentés. Ne pas renvoyer tout le site ni doubler le même lot par plusieurs méthodes. Une réponse acceptée prouve la réception de la notification, pas l’indexation.
7. **Vérifier et consigner les résultats.** Séparer propriété créée, propriété vérifiée, sitemap soumis, sitemap lu, URL découverte, URL explorée, URL indexée et données de recherche. Après une réponse incertaine, vérifier le statut avant toute répétition. Si le résultat d’indexation n’est pas encore disponible, le laisser en attente et proposer un contrôle adapté.

### Bing : diagnostiquer une propriété existante avec peu ou pas de données

Ne pas traiter une faible activité comme un mauvais réglage avant d’avoir vérifié la propriété et les rapports.

- Confirmer que la propriété sélectionnée correspond au domaine, à l’hôte et au périmètre de l’URL canonique. Vérifier les dates, filtres et droits du compte.
- Si la propriété vient d’être ajoutée ou vérifiée, tenir compte du délai de collecte documenté. Pour un site déjà ancien, poursuivre le diagnostic plutôt que supposer que les données vont apparaître d’elles-mêmes.
- Vérifier l’état du sitemap, puis utiliser Site Explorer pour repérer URL non explorée, erreur serveur, blocage robots.txt, noindex, redirection, problème de canonical, problème de règles ou logiciel malveillant. Inspecter les URL prioritaires avec le rapport d’indexation et le test live.
- Utiliser le robots.txt tester pour repérer une règle qui bloque Bingbot. Examiner les réponses HTTP, les canonicals, le rendu public, les logs d’origine et les règles CDN/WAF ; vérifier l’identité réelle de Bingbot au lieu de se fier au seul User-Agent.
- Consulter Crawl Control seulement si un ralentissement ou une surcharge est observé. Ne pas augmenter la vitesse de crawl à l’aveugle ; une directive crawl-delay de robots.txt peut prévaloir sur ce réglage.
- Vérifier les signaux de découverte et de qualité : liens internes explorables, URL dupliquées ou de faible valeur, contenu rendu et liens externes pertinents. Si le site est vérifié depuis plusieurs jours et que les rapports restent vides malgré un crawl techniquement accessible, rassembler les preuves puis ouvrir une demande au support Bing.

## Contrôle technique ciblé et corrections

Les vérifications d’indexation doivent d’abord confirmer, sur le sitemap et les pages soumises, une réponse HTTP exploitable après redirection, un accès public au crawl, l’absence de noindex non voulu, une canonical cohérente et une présence dans le sitemap uniquement pour les pages canoniques destinées à l’indexation. Une anomalie limitée à un sous-ensemble ne doit pas suspendre les démarches sur les URL éligibles.

Pour une correction ou une republication, appliquer les [contrôles dépôt, publication et indexation](../seo/references/production-indexation.md) : vérifier le domaine public, le dépôt et le déploiement effectif, préserver les pages déjà publiées et contrôler à nouveau après publication. Un audit complet page par page, du maillage, des gabarits ou des intentions reste possible lorsqu’il est demandé ou nécessaire pour expliquer une exclusion ; il ne constitue pas une condition préalable à l’accès en lecture aux propriétés et rapports.

Contrôler HTTPS, redirections et hôte final, réponses HTTP, robots.txt, meta robots et X-Robots-Tag, canonical, contenu HTML accessible, maillage et sitemaps. Examiner CDN/WAF et logs si disponibles. Une simulation d’user-agent ne prouve pas l’accès du robot réel.

Sitemaps : format valide, URLs absolues canoniques, indexables et publiques, index/enfants accessibles, dates lastmod exactes, limites officielles respectées. Exclure preview, administration, données privées, paramètres inutiles et pages non destinées à la recherche. Ne pas indexer une page volontairement privée ou noindex. Les notifications de suppression IndexNow suivent une voie distincte et peuvent concerner des URLs supprimées.

robots.txt gère le crawl et ne protège pas des données privées ; une URL bloquée peut encore apparaître dans Google. Un noindex doit être accessible au robot pour être lu. Ne pas ouvrir une page privée pour rendre son noindex lisible : conserver son contrôle d’accès. Valider le format existant du sitemap plutôt qu’imposer XML : Google accepte aussi les formats texte, RSS et Atom documentés.

Corriger les blocages démontrés dans le périmètre autorisé, avec la stack existante et un diff vérifiable. Ne pas refaire le design. Une correction locale n’est pas une correction en production : respecter les droits de déploiement et vérifier l’état public après publication. Si un blocage touche un sous-ensemble, poursuivre les démarches des pages éligibles et signaler les exclusions.

## Effectuer les démarches

1. **Google Search Console** : suivre le parcours d’indexation ci-dessus. Réutiliser la propriété qui couvre exactement le domaine ; si elle manque dans le compte et que l’opération est demandée, l’ajouter par l’API Sites.add ou l’interface, puis vérifier la propriété par une méthode autorisée. Un ajout API ne remplace pas la preuve de propriété. Une propriété Domaine requiert une preuve DNS ; ne modifier les DNS que si cette action est explicitement autorisée et accessible. Vérifier le rôle requis pour l’action et soumettre le sitemap valide par l’interface ou l’API Sitemaps.submit. Utiliser l’inspection URL pour le statut indexé ; l’API d’inspection est en lecture seule. Les demandes individuelles de nouvelle exploration passent par l’interface et son quota réel ; ne pas utiliser l’Indexing API générale pour des articles ou fiches ordinaires.
2. **Bing Webmaster Tools** : suivre le parcours d’indexation ci-dessus. Créer la propriété si elle manque et que la demande opérationnelle le permet, de préférence par import GSC autorisé ; vérifier son statut et le sitemap importé avant toute nouvelle soumission. Soumettre jusqu’à 100 URL canoniques éligibles par exécution, ou moins si le quota disponible est inférieur. Utiliser IndexNow pour les changements réels quand une intégration existe. Pour une propriété ancienne sans données ou avec peu d’URL indexées, appliquer la branche de diagnostic Bing avant de modifier Crawl Control ou d’autres réglages.
3. **IndexNow** : rechercher l'intégration CMS/CDN existante avant d'en créer une seconde. Vérifier la clé et son fichier public sur l'hôte concerné ; respecter keyLocation, portée du chemin, formats, taille des lots et participants documentés. Séparer les hôtes en lots distincts. Soumettre les URLs créées, modifiées ou supprimées réellement concernées. Une notification à un participant peut être partagée entre participants : ne pas multiplier les envois par moteur. HTTP 200 signifie notification reçue, 202 validation de clé en attente ; aucun ne prouve l'indexation. Diagnostiquer 403 (clé), 422 (hôte/format) et 429 (limitation) avant reprise. Google n'est pas couvert implicitement.
4. **Moteurs complémentaires pertinents** :
   - **Brave Search** possède son propre index. Sa documentation indique que son crawler n'utilise pas d'agent utilisateur distinct et ne peut pas explorer une page inaccessible à Googlebot. Vérifier l'accès public de Googlebot et les blocages CDN/WAF. `robots.txt` n'est pas son mécanisme de désindexation ; utiliser `noindex` pour demander le retrait, puis la procédure Brave de relecture/désindexation si nécessaire. Le formulaire de relecture n'est pas une soumission initiale garantie. [Documentation Brave](https://search.brave.com/help/brave-search-crawler).
   - **Qwant / EUSP** : vérifier que QwantBot n'est pas bloqué, que l'URL renvoie du HTML public exploitable, que le sitemap est accessible et qu'aucun `noindex` ne s'applique. Qwant découvre les pages par liens ou sitemap. Si une page reste absente après diagnostic, suivre la procédure officielle « mon site n'apparaît pas » et transmettre URL, diagnostic et date de mise en ligne. [Indexation Qwant](https://help.qwant.com/hc/fr-fr/articles/49002658519569-Comment-Qwant-indexe-le-web) · [Diagnostic Qwant](https://help.qwant.com/hc/fr-fr/articles/49027002807313-Pourquoi-mon-site-n-appara%C3%AEt-il-pas-dans-les-r%C3%A9sultats-Qwant).
   - **Ecosia** : en France, une partie des résultats provient de l'index EUSP construit avec Qwant et Ecosia. Le fournisseur varie selon le pays, l'appareil, les réglages de confidentialité et la requête. Ce n'est pas une soumission Ecosia distincte à présumer. [Fournisseurs Ecosia](https://fr.support.ecosia.org/article/899-search-result-providers).
   - **DuckDuckGo** : préserver la découvrabilité Bing et l'accès de DuckDuckBot ; ses résultats s'appuient sur des sources partenaires et sur son propre crawl. Ne pas inventer un portail de soumission dédié si aucune procédure officielle actuelle n'est documentée. [Sources DuckDuckGo](https://duckduckgo.com/duckduckgo-help-pages/results/sources) · [DuckDuckBot](https://duckduckgo.com/duckduckgo-help-pages/results/duckduckbot).
   - **IndexNow** : relire la liste officielle et dynamique des participants avant intégration. Notifier uniquement les URL canoniques nouvelles, modifiées ou supprimées. L'accusé confirme la notification, pas l'exploration ni l'indexation. Ne pas présumer Google, Qwant, Brave ou un moteur IA participant sans preuve dans la liste officielle. [Participants IndexNow](https://www.indexnow.org/searchengines) · [FAQ](https://www.indexnow.org/faq).
5. **Recherche IA** : contrôler séparément les robots de recherche, d'entraînement et de récupération à la demande. Pour ChatGPT Search, `OAI-SearchBot` concerne les résultats, `GPTBot` l'entraînement et `ChatGPT-User` les actions déclenchées par les utilisateurs ; autoriser le premier ne requiert pas d'autoriser les autres. Pour Perplexity, distinguer `PerplexityBot` (découverte dans les résultats) de `Perplexity-User` (requêtes utilisateur). Pour Claude, distinguer `Claude-SearchBot`, `ClaudeBot` et `Claude-User`. Si un CDN/WAF filtre ces robots, vérifier leur identité avec les plages IP publiées et actualisées, lorsque le fournisseur en publie ; ne jamais se fier au seul User-Agent ni ouvrir largement le pare-feu. Respecter la politique d'entraînement du site. [Robots OpenAI](https://developers.openai.com/api/docs/bots) · [robots Perplexity](https://docs.perplexity.ai/docs/resources/perplexity-crawlers) · [robots Anthropic](https://support.anthropic.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler). Ne pas présenter llms.txt ou IndexNow comme une soumission universelle à ChatGPT, Claude, Gemini ou Perplexity.
6. **Modules conditionnels** : activité locale réellement éligible, commerce, images, vidéos, actualités et annuaires professionnels pertinents. Vérifier éligibilité, identité et informations réelles avant toute fiche. Ne pas créer de compte, payer, accepter un contrat nouveau, publier une campagne, contacter des tiers ou diffuser des données personnelles sans autorisation adaptée. Préparer les dossiers et continuer les démarches indépendantes si une validation humaine manque.

Privilégier API/connecteurs officiels ; utiliser une session navigateur autorisée si nécessaire et disponible. En cas de connexion, MFA, CAPTCHA ou preuve de propriété manquante, demander uniquement l'intervention indispensable sans contourner le contrôle. Ne pas arrêter tout le workflow pour un seul opérateur inaccessible.

## Relier GA4 et Clarity (facultatif)

Pour GA4 et Clarity, inventorier les comptes, propriétés, flux, tags, consentements, intégrations et données observées. Les propriétés GSC et Bing, leurs sitemaps et leur état d’indexation sont gérés dans le parcours précédent ; une étape de mesure ne doit pas retarder ces démarches. Distinguer absent, installé, lié, vérifié, accessible et données reçues. Ne jamais demander de mot de passe, créer un compte, publier un tag/script, changer DNS ou modifier la plateforme de consentement sans autorisation explicite.

Suivre le graphe réel des intégrations, sans promettre de lien natif Analytics–Bing :

- **GA4 ↔ Search Console** : appliquer la [procédure GA4–Search Console](../analytics/references/search-console-link.md). Lire les associations avant création ; vérifier le couple propriété GSC/flux web GA4, leur portée et les rôles requis. Réutiliser l'association correcte ; ne jamais supprimer/recréer un lien occupé ou erroné sans mandat adapté.
- **GA4 ↔ Microsoft Clarity** : une fois GA4 et le projet Clarity configurés, proposer et réaliser, si autorisé et disponible, l'association dans Clarity. Vérifier la propriété/flux sélectionné et noter les limites de portée. L'association ne remplace pas l'installation de la collecte Clarity sur le site.
- **Bing Webmaster Tools ↔ Clarity** : utiliser l'intégration Clarity disponible dans Bing Webmaster Tools si le compte et la propriété le permettent ; confirmer le site exact et l'état affiché.

Sources officielles à revalider au moment de la configuration : [lier GA4 à Clarity](https://learn.microsoft.com/en-us/clarity/ga-integration/ga-integration), [FAQ Microsoft Clarity](https://learn.microsoft.com/en-us/clarity/faq), [intégration Clarity de Bing Webmaster Tools](https://www.bing.com/webmasters/help/webmaster-support-24ab5ebf), [importer/vérifier un site depuis Search Console dans Bing](https://www2.bing.com/webmasters/help/add-and-verify-site-12184f8b). Ces intégrations et leurs conditions peuvent évoluer.

L’indexation GSC/Bing n’attend pas GA4 ou Clarity. Traiter leurs propriétés et sitemaps selon le parcours précédent, puis configurer GA4/Clarity si le site et l’autorisation le permettent. Si GA4 manque, demander l’accès ou l’intervention minimale pour créer le compte, la propriété et le flux web, puis confirmer séparément la collecte. Poursuivre les démarches indépendantes sans inventer de lien ni de résultat.

Vérifier et consigner séparément propriété créée/vérifiée, tag installé, consentement préservé, association configurée, rapports accessibles et données disponibles ; observer une période éligible et tenir compte des délais documentés. Une liaison n'autorise pas à elle seule un nouveau tag ni une collecte sans consentement requis. Ne jamais assimiler clics GSC à sessions GA4, impressions Bing aux impressions Google, réception de sitemap à indexation, ni configuration réussie à collecte observée. En l'absence de lien Analytics–Bing natif, exploiter séparément leurs rapports et comparer des périodes/périmètres explicites. Après résultat d'écriture inconnu, rechercher l'association avant réessai.

## Optimiser la visibilité après déploiement

Appliquer [la boucle d’optimisation de recherche](references/search-optimization.md) sur les données réelles du site : indexabilité/exploration, requêtes/pages GSC et Bing accessibles, engagement/événements clés GA4 consent-aware, visibilité IA observée avec limites. Comparer périodes/filtres/volumes et saisonnalité ; prioriser intentions, catalogue, maillage, métadonnées et performance démontrés. Réutiliser SEO méthodologie, SEO contenu et IA sans récursion, production massive ni promesse de classement. Sans données : baseline et attente documentées. Séparer recommandations, corrections locales autorisées, publication et écritures de comptes ; consigner historique, preuves, hypothèses et réévaluation sans automation implicite.

## Tenir le registre et reprendre

Réutiliser le dossier SEO ; sinon créer SEO/POST_DEPLOY/. Conserver un registre lisible, éventuellement JSON, par domaine et opérateur : propriété, sitemap/URLs, action, date, preuve non sensible, statut, erreur, accès manquant et prochaine action. Statuts utiles : A_FAIRE, FAIT_VERIFIE, SOUMIS_EN_ATTENTE, BLOQUE_ACCES, BLOQUE_TECHNIQUE, NON_APPLICABLE, NON_VERIFIE. Séparer soumission acceptée, sitemap lu, URL indexée, impressions/clics et visibilité IA.

À chaque relance, lire le registre et l'état réel : ne pas recréer une propriété ni soumettre les mêmes URLs inchangées. Reprendre les opérations inachevées ou justifiées par les changements. Avant de réessayer une écriture dont le résultat est inconnu, vérifier si elle a abouti. Respecter quotas et Retry-After ; après deux échecs comparables sans nouveau diagnostic, consigner le blocage et poursuivre ailleurs. Ne pas lancer des scans coûteux ou répétés pour remplir un rapport.

Si une écriture expire sans réponse et qu'aucun statut fiable ne permet de conclure, conserver NON_VERIFIE avec action/lot/date et résultat inconnu ; suspendre sa répétition automatique. L'absence de preuve d'indexation ne prouve pas l'échec de la soumission. Une recherche site: est un indice de visibilité ponctuel, pas un inventaire exhaustif ni une preuve d'absence de l'index.

Proposer des contrôles à J+3, J+7 et J+30 adaptés au projet : lecture des sitemaps, couverture, erreurs, pages prioritaires et premières données de recherche. Une proposition n'est pas une automation créée. Programmer un suivi uniquement sur demande explicite, avec l'outil officiel et notification seulement en cas de changement utile ou intervention nécessaire.

Livrer un bilan concis : site exact, opérateurs couverts/exclus et raisons, démarches exécutées et preuves, corrections publiées ou locales, pages soumises/indexées observées, limites et interventions restantes. Ne déclarer complet que le périmètre effectivement exécuté ; une indexation future reste en attente.

## Scénarios de vérification du skill

Pour les fixtures et le déroulé manuel, lire [les scénarios](references/scenarios.md). Ils vérifient la cohérence des décisions ; ils ne prouvent ni l'exécution par un agent indépendant ni le fonctionnement d'une intégration réelle.

- Nouveau site sans propriété dans les comptes accessibles : pour une demande opérationnelle d’indexation, tenter l’ajout GSC/Bing avec les droits disponibles ; marquer la vérification BLOQUE_ACCES si une preuve ou une intervention DNS autorisée manque, sans inventer de réussite.
- Site déjà présent dans Google/Bing : réutiliser les propriétés et sitemaps ; traiter les nouveaux changements sans doublons.
- Blog ordinaire : sitemap/Search Console ; aucune utilisation abusive de Google Indexing API.
- Preview noindex et production publique : traiter seulement la production ; préserver la preview.
- Avant une écriture GSC/Bing : consulter d’abord les propriétés et rapports accessibles ; valider le sitemap et exclure les URL non indexables avant soumission. Un contrôle exhaustif du contenu de chaque page n’est pas un préalable à la lecture des outils.
- GSC/Bing et mesure : ne pas bloquer l’indexation à cause de GA4/Clarity ; créer/réutiliser les propriétés d’indexation seulement dans le cadre autorisé ; préserver les consentements et ne pas publier de nouveau tag sans accord.
- IndexNow accepte une notification mais aucune preuve d'indexation : statut de soumission uniquement.
- Une page Qwant absente après contrôle du HTML, sitemap, robots et `noindex` : suivre la procédure officielle d'aide Qwant et conserver la demande comme démarche, pas comme indexation acquise.
- Brave ne ressort pas une URL : contrôler d'abord l'accès à Googlebot ; ne pas traiter le formulaire de relecture/retrait comme une soumission garantie.
- Ecosia change de fournisseur selon la requête : consigner le fournisseur indiqué et ne pas attribuer l'écart à une indexation Ecosia unique.
- Site local non éligible ou marché hors cible : exclure les fiches/modules concernés avec raison.
- GSC URL Inspection API : lecture seule ; les demandes Google individuelles passent par l’interface et son quota disponible.
- Bing vérifié depuis longtemps mais sans données : vérifier la propriété, les dates, le sitemap, Site Explorer, robots.txt, Crawl Control, CDN/WAF et qualité avant de conclure ; le support est la suite si les rapports restent vides.
- Soumission Bing : plafonner à 100 URL uniques éligibles par exécution même si le quota officiel affiché est supérieur ; le plafond est une règle de workflow, pas une affirmation de quota plateforme.
