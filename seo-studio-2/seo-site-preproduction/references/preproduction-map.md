# Preproduction map: adapt the model to the niche

This map extracts reusable relationships from the bundled example. It is a set of
questions for project-specific preproduction, not a mandatory sitemap or design.

## SEO and content architecture

| Possible pattern in the demo | Preproduction question for the requested niche |
|---|---|
| Home with a decision-oriented tool | What is the first useful task a visitor can complete here? Use a tool only if its result can be grounded and maintained. For affiliate sites, show verified product choices and direct offers before a tool; the bundled tool-first sofa home is not a passing affiliate landing. |
| Commercial entry and product families (when the model is affiliate) | Which verified products answer the main need now? Put real product imagery, exact references, dated prices and usable affiliate CTAs in the first useful viewport. Derive category hubs from benchmarked demand and verified attributes; keep unsupported combinations as UI filters or omit them. |
| Category/choice page | Which distinct decision or search intent deserves a hub? Define eligibility, filters, limits and its supporting prose. |
| Practical guide | What must the reader understand or do before choosing? Build the guide from evidence and real workflow, not keyword variations. |
| Product/model detail | Does the niche need a record for a specific item, service, location or case? Define data provenance, missing states, update cadence and when no detail page is justified. |
| Method/transparency page | What method, author, commercial relationship, limits or governance does this site actually need to explain? |

For each page candidate, record audience task, query/intent evidence, unique answer,
URL, indexability decision, source owner, internal links in and out, conversion role,
maintenance trigger and acceptance evidence. Do not create indexable variants from
filters alone. Do not require a product page, affiliate module or programmatic SEO
when the niche and user request do not support it.

## UI/UX structure

Map the decision journey before reusing components. The sofa demo uses a measurable
constraint as its opening gesture; another niche may need a diagnosis, eligibility
check, location, budget, timeline, compatibility question or no interactive tool.
On an affiliate site, verified product access remains ahead of optional tools and
long editorial routes on the entry page.
For each proposed interaction, define:

- its user problem and input data;
- the result logic, provenance and uncertainty behavior;
- keyboard, screen-reader, mobile, empty and error states;
- the next useful page or action;
- whether the experience works without JavaScript or an external service.

Specify shared navigation, page templates, card/detail relationships, disclosure,
sticky elements, search/filter behavior and responsive hierarchy only after the
niche's journeys are known. A page family is not a reason to create a repeated card
grid. A high-impact action should be visible with its relevant evidence and limits.

## Prose, proof and persuasion

Use `redaction-editoriale-web` for actual reader-facing prose. The demo's useful
selling sequence is an example: name the concrete decision, help rule out a poor
fit, compare documented facts, state unknowns and present the relevant next step.
Adapt that sequence to the real niche and buying process.

For each page and CTA, decide:

1. Which question or objection is being answered?
2. Which fact or source supports the statement?
3. What limitation or missing information could change the decision?
4. Why is the proposed CTA the next useful action?
5. Does compensation affect placement, and how is that relationship disclosed?

Do not invent expertise, tests, prices, availability, reviews, guarantees, partners,
or urgency. Avoid generic superiority claims, keyword-stuffed headings, empty
superlatives and sales copy that withholds an answer only to induce a click. Keep
the reader's decision complete even when commercial modules are removed.

## Studio 2 phase mapping

- **G2 — architecture:** candidate page families, query/task ownership, URL and
  indexing policy, taxonomy, navigation and the internal-link graph.
- **G3 — experience and content:** project-specific skin, responsive journeys,
  component states, briefs, editorial rules, pilot copy and supported conversion.
- **G4 — realization plan:** technical dependencies, evidence capture, performance,
  accessibility and measurement requirements in Studio's existing artifacts.
- **G5 — review and handoff:** demonstrate that sample-only nouns/assets were
  removed or deliberately retained for the requested niche; link review evidence
  to existing QA and decision registers.

This map adds no approval gate and does not replace Studio 2's existing F0–F3,
partner, quality or handoff requirements.
